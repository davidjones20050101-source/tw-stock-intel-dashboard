先建立正確心智模型

Codex 不是聊天機器人，是工程協作 Agent

它可以讀專案、規劃修改、編輯檔案、跑測試、整理 diff，最後交給人審查。
理解：讀 repo、文件、錯誤訊息
行動：修改、補測試、整理文件
驗證：lint、test、build、review
交付：摘要、差異、風險、下一步

第一階段

入口怎麼選？

不同入口適合不同工作，不要全部混在一起用。
ChatGPT：需求整理、雲端任務、跨檔案討論

第二階段

新手第一個 Prompt：不要只說『幫我做』

好的任務要有目標、範圍、限制、驗證、輸出格式。
目標：要解決什麼
範圍：哪些能改、哪些不能改
驗證：要跑什麼測試
輸出：要回報什麼證據

Prompt 模板 1

理解專案，不要修改

用在剛接手陌生 repo 的第一步。
請先閱讀 README、package.json 與主要資料夾

列出資料流與啟動方式
不要修改任何檔案

Prompt 模板 2

修一個小 bug

新手最容易成功的任務是『範圍小、結果可驗證』。
目標：修正手機版登入按鈕被遮住
範圍：只改 login 頁與相關 CSS
驗證：跑 lint/test，必要時截圖
輸出：摘要、diff、風險、回滾方式

第五階段

Cloud Task 怎麼派？

Cloud 的重點不是『丟出去就不管』，而是『把明確任務交給隔離環境，回來審結果』。
一任務一目標
限制可修改範圍
要求驗證命令
要求列出風險
最後人工決定是否開 PR / 合併

Cloud 任務範例

適合丟給 Cloud 的 5 類任務

這些任務通常有明確輸入、可驗證輸出，而且不用一直互動。
補測試覆蓋率
升級套件並修相容性
清理 lint/type error
重構單一模組
把文件更新成最新狀態
22 / 34
Cloud 不適合什麼？

這些任務不要一開始就丟雲端

新手最常犯的錯，是把還沒想清楚的產品決策丟給 Agent。
還沒定義的產品方向
涉及正式資料庫或金流
需要大量主觀設計判斷
沒有測試可驗證的核心改動

權限設計

新手安全邊界

權限不是越大越好；越清楚，結果越穩。
讀取：排除機密與客戶資料
寫入：先限制功能資料夾
命令：測試可放寬，部署要批准
網路：需要查文件時再開
29 / 34
審查清單

不要只看它說『完成』

交付前一定要看證據。
是否真的改到需求範圍？
diff 是否過大或不相關？
測試是否真的執行且通過？
有沒有列出未驗證風險？
是否知道怎麼回滾？

常見錯誤

新手最容易踩的 7 個坑

避開這些，成功率會高很多。
任務太大
沒有指定不可改範圍
沒有要求測試
把機密資料貼進去
不看 diff 就合併
讓它直接部署
